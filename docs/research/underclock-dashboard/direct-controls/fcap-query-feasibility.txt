Actualstock qcom-scm.ko ABI matches relevant public helpers:
* qcom_scm_lmh_dcvsh_available @0x4590: INFO service6/command1 check of LMH service0x13/command0x10. This establishes only command-handler availability, not supported algorithms/settings/nodes nor SRB enforcement.
* qcom_scm_is_lmh_debug_get_type_available @0x4ac4: LMH service0x13/command0x0b handler availability.
* qcom_scm_lmh_get_type @0x40c8: command0x0b; args [physical DMA output buffer, byte capacity, debug_type, starting index], 4-argument descriptor0x24 (RW,VAL,VAL,VAL); optional returned totalcount pointer.
* qcom_get_scm_device @0x82e4 is exported. A correctlybuilt kernel query bridge can allocate/free coherent DMA against SCM's actual device; no raw pointer/virt_to_phys buffer or direct register/SMC code necessary.

Known LMH GET_TYPE enumeration semantics from older Qualcomm lmh_dbg.c:
https://android.googlesource.com/kernel/msm.git/+/d616c9a54122060c1d23b0de1302746b362dd4b2/drivers/thermal/qcom/lmh_dbg.c
* debug_type0 = read/data types; debug_type1 = config types.
* buffer10 u32 entries; query starts index0; firmware return gives total entries; paginate starting10,20,...
* this enumeration calls GET_TYPE only. It neither changes limits nor invokes DEBUG_SET.
* legacy read-only debugfs endpoints /sys/kernel/debug/lmh_monitor/data_types and config_types would be ready-made if present. Modern related source has no lmh_dbg.c frontend; existenceofexportedhelpers doesnotprovideuserspaceentrypoint.
* these are LMH debug-interface command categories. DEBUG_SET uses service0x13/command0x08. FCAP is a DCVSH setting in separate service0x13/command0x10 payload. No guarantee that GET_TYPE enumerates FCAP setting itself. An enumlistcannotproveFCAPworks orSRBisclamped.
